How Can a Powerful AI Model Fit on a Phone?

What must change before a trained AI model can run well on a phone, and how can we test the trade-offs?

Research checked 29 October 2026 · Two worked examples are illustrative · Original source dates below

Executive summary

A large AI model can require more memory and energy than a phone can supply. Researchers have developed several ways to reduce the cost of running a model after training. Quantization stores numbers with fewer bits. Distillation trains a smaller student model to copy useful patterns from a larger teacher. Efficient architecture changes the operations a model performs. Each method saves a different resource, and each can reduce quality. A model that occupies less storage does not always answer faster. It may still need memory for temporary calculations and for the growing text of a conversation. Hardware support, heat, battery use and the length of the task also matter. Original studies of mobile vision models, integer arithmetic and compressed language models show major gains under specified tests. Their results do not guarantee equal gains on every device. This guide explains the engineering steps, gives two transparent calculations, compares the evidence, and shows how to test an on-device system. Local execution can improve control over data, but privacy depends on the complete application.

1. The central question: what must fit?

A model can be excellent on a server and unusable on a mobile device. The device must hold the model's weights, run its calculations, and keep temporary information while it produces an answer. It must do this within a limit on battery power, heat, storage and memory. A model that fits in a download may still fail to start because its working memory is too large. A model that starts may become too slow after the user adds a long document.

The central question is therefore more precise than whether a model can be made small. It is: can the full application finish a defined task, at an acceptable quality, speed and energy cost, on a specified device? This is a systems question. Model design, number formats, software kernels and hardware must work together. The original research on efficient neural networks and compression gives methods for improving these trade-offs. It does not remove the need to measure the final product. See the early mobile work by Jacob and colleagues [2] and Sandler and colleagues [3].

2. Essential terms: weights, bits, inference and memory

A parameter is a learned number that helps determine a model's output. A weight is a common type of parameter. Inference means running the trained model to make a prediction or produce text. Precision is the number format used to store and calculate values. A bit can hold two states; more bits can represent more possible values. Common formats include 32-bit floating point, 16-bit floating point, 8-bit integer and 4-bit packed weights.

Quantization maps many precise values to a smaller set of values. Distillation trains a smaller model using the outputs of a larger model. Pruning removes selected connections or units. Latency is the delay before or during an answer. Throughput is the amount of work completed per unit time. Bandwidth is how quickly data moves between memory and processing units. These words describe different limits. Reducing one does not guarantee an improvement in the others.

For text generation, the key-value cache stores intermediate attention information for earlier tokens. It can grow with conversation length. Calibration data is a small sample used to select a suitable numerical representation during compression. It must cover realistic inputs or the compressed model can fail in unexpected cases.

3. How the field developed

Research on smaller neural networks began long before chat assistants became common. In March 2015, Hinton, Vinyals and Dean described knowledge distillation: a student can learn from the full probability pattern produced by a larger teacher. The important insight is that the teacher's second and third choices can carry useful information about relationships between categories [1]. A student can learn more than it would from a single correct label.

By June 2018, work on mobile vision had focused on efficient operations and integer arithmetic. MobileNetV2 used a carefully designed architecture to reduce computational cost. Jacob and colleagues demonstrated integer-only inference and quantization-aware training for image tasks on mobile-class processors [2][3]. These studies addressed specific image benchmarks, not the full range of modern language tasks.

The large-language-model period brought a new memory problem. Dettmers and colleagues studied 8-bit matrix operations in transformers at NeurIPS 2022 [4]. GPTQ, first posted in October 2022 and later presented at ICLR 2023, examined accurate 3-bit and 4-bit post-training weight compression [5]. AWQ, published at MLSys 2024, protected important weights based on observed activations [6]. These papers provide a progression of methods, not a single universal recipe.

4. Step one: measure the uncompressed system

An engineer must first define a baseline. Choose the exact model version, device, operating system, runtime, task set and acceptable answer quality. Measure storage used by the model, memory at startup, peak memory during use, time to first output, tokens per second, total battery consumption and device temperature. Also record the length of each input. A short prompt can hide problems that appear after several minutes of conversation.

Next, divide the system into parts. Model weights occupy relatively stable memory. Activations are temporary results of each operation. The key-value cache often increases as text length grows. The runtime adds buffers and code. The application adds its own data and interface. These parts compete for the same physical memory. A phone with a given amount of RAM cannot dedicate all of it to the model because the operating system and other applications need space.

Quality needs a baseline too. A single public benchmark is not enough. Include representative tasks, difficult inputs, different languages, safety checks and repeat trials. Compression can change rare but important responses while leaving average test scores almost unchanged. Without a baseline, later speed claims have no useful meaning.

5. Step two: reduce precision with quantization

A trained model often stores many weights in a 16-bit or 32-bit format. Quantization replaces those numbers with a smaller code and a rule for converting that code into a useful numerical value. For a group of weights, software can record a scale and sometimes an offset. A low-bit integer then represents a nearby point on that group's numerical range. The operation is approximate: some original information is lost.

One method changes the number format after training. This is post-training quantization. Another exposes the model to quantization effects during training, so it learns to work with them. This is quantization-aware training. Jacob and colleagues studied the latter approach for integer-only vision inference and reported a close-to-fourfold weight-memory reduction when moving from 32-bit values to 8-bit values, with the qualification that the whole system's speed and accuracy depend on implementation [2].

A simple rounding rule can damage the model because some weights are more sensitive than others. Modern methods use sample activations or error estimates to choose how to round and scale weights. Quantization must also account for computation: a 4-bit file is of little use if the device constantly expands it into a costly format or has no efficient operation for it.

6. Step three: protect sensitive numbers

Transformers sometimes contain activation values that are much larger than most values in the same calculation. A uniform small numerical range can lose useful information when it tries to represent both ordinary values and these outliers. Dettmers and colleagues proposed LLM.int8(), which performs most operations in 8-bit precision but keeps selected outlier dimensions at higher precision. Their NeurIPS 2022 study reports that this mixed approach preserves model performance on their tested large transformer systems [4].

GPTQ takes a different route. It estimates how rounding one weight changes the output of a layer, then adjusts other weights to reduce the damage. Its original paper reports compression to 3 or 4 bits per weight on large models, with measured speedups using purpose-built execution code [5]. The exact gains belong to those experiments and hardware configurations.

AWQ uses the size of observed activations to identify important weight channels. It then applies scaling that protects those weights during low-bit compression. The MLSys 2024 authors report more than threefold speedups against their stated FP16 implementation on tested desktop and mobile GPU settings [6]. The three methods illustrate the same general rule: spend precision where errors matter most. Their assumptions and benchmarks are different, so their speed figures should not be added or compared without a common test.

7. Step four: train a smaller student

Quantization keeps the broad structure of an existing model and changes how its numbers are represented. Distillation changes the model itself. A large teacher produces outputs on selected inputs. A smaller student learns to match these outputs, often alongside correct labels. In classification, the teacher's probabilities show which wrong answers are close to the right one. Hinton and colleagues called these soft targets and described how temperature changes the shape of the probability distribution [1].

For a language model, a student can learn from teacher-generated responses, token probabilities or task-specific examples. A useful student may need fewer parameters and fewer calculations. But it has a limited capacity. It can miss unusual cases, lose multilingual performance or copy the teacher's mistakes. It can also learn from errors in generated training data. A student is not an exact archive of the teacher's knowledge.

Distillation is especially useful when the final application has a narrow, well-defined job. A small system for classifying a fixed set of documents may need less general knowledge than an open-ended assistant. The engineer should test the student against both the teacher and independent ground truth. Agreement with a teacher is not the same as correctness.

8. Step five: choose operations the device can run well

A small parameter count is helpful, but it is not a complete measure of efficiency. Two models with similar parameter counts can use very different operations. Some operations move large blocks of data. Others require many sequential steps. A processor may be fast at one type and slow at another. The software library may support one format efficiently but handle another through costly conversion.

MobileNetV2 showed how architecture can improve the trade-off between accuracy and computation for mobile vision. It used inverted residual blocks, depthwise convolution and linear bottlenecks, and evaluated the results on standard image tasks [3]. Those ideas cannot be transferred directly to every transformer, but the design principle remains: choose an architecture with the actual target hardware in mind.

For text generation, the prompt-processing phase and token-generation phase also behave differently. Processing a long prompt can use parallel work. Producing each new token often requires repeated reading of model weights and attention state. An implementation that excels at the first phase can still be slow in the second. The correct test therefore includes both phases and the full input range expected in use.

9. Diagram: from large model to a measured phone app

The diagram shows three possible interventions and one shared verification step. Distillation produces a new student. Quantization changes number formats. Runtime and architecture work changes how operations execute. The arrows do not imply that every project needs all three interventions or that each gives a fixed improvement.

An important design decision is where to spend the remaining resources. A product might accept a small loss in a low-risk classification task to gain offline access. It might reject the same loss in a medical or legal setting. The task's error cost must be part of the evaluation. Model size alone cannot set this threshold.

10. Worked example one: calculate weight storage

Illustrative calculation, not a measurement of a product. Consider a model with 3 billion parameters. If every parameter uses 16 bits, raw weight storage is 3,000,000,000 × 16 ÷ 8 = 6,000,000,000 bytes, or about 6.0 GB in decimal units. If every parameter instead uses 4 bits, the theoretical raw storage becomes 1.5 GB. The theoretical reduction is 75%. The ratio is four to one because 16 ÷ 4 = 4.

This calculation leaves out scale values, offsets, packing overhead, embeddings that may remain in higher precision, runtime buffers, activations and the key-value cache. The application may also keep a second copy of some weights during loading. A 1.5 GB weight file does not mean the model can run with only 1.5 GB of free RAM. It also does not show whether the compressed model is accurate enough.

The lesson is to distinguish raw weight arithmetic from measured peak system memory. The first can be calculated from parameter count and bit width. The second must be measured on the device.

11. Worked example two: measure real speed

Illustrative test, not a published benchmark. A team compares two versions of one assistant on the same phone, with the same prompt and a fixed 200-token output. The baseline takes 10 seconds before its first token and 20 more seconds to finish. The compressed version takes 6 seconds before its first token and 16 more seconds to finish. Total time falls from 30 to 22 seconds. The speedup is 30 ÷ 22 = about 1.36 times, and the reduction in total delay is about 26.7%.

This does not establish that the compressed model is better. The team must check answer quality, energy use, heat and performance after repeated runs. It must also test longer prompts. If the compressed version makes more factual errors or overheats after five minutes, the speed result may be unacceptable. If the application runs offline and meets its quality target, the trade-off may be useful.

Report the full test setup: device model, processor, memory, software version, prompt length, output length, temperature, number of trials and the spread of results. Without these details, a speedup figure is hard to reproduce.

12. What the original studies establish—and what they do not

The strongest evidence in this field comes from controlled comparisons within individual studies. Jacob and colleagues showed that integer arithmetic can improve the speed and memory trade-off for tested mobile vision networks [2]. Hinton and colleagues showed that teacher outputs can train a smaller student effectively on their studied tasks [1]. Dettmers, Frantar and Lin each reported ways to reduce transformer weight cost while retaining much of the measured quality [4][5][6].

The limits are equally important. A result on one model family may not hold for another. A result on a server GPU may not hold for a phone's neural accelerator. Different papers use different evaluation tasks, precisions and baselines. Some results concern perplexity, which measures how well a model predicts text, rather than whether it gives safe and correct answers to users. Some speedups require custom kernels that are not available on every device.

Publication dates also matter. A 2018 mobile vision result is evidence for its method and hardware era. A 2024 compression result is evidence for the tested transformer systems. Neither is a current device-buying recommendation. A sound engineering decision needs fresh measurements on the intended device.

13. Competing views: local, cloud or hybrid?

A strong case for local inference is control. An application can work without a network, reduce server dependence and keep some user data on the device. It can also reduce repeated transmission of private inputs. This is a practical benefit when the software truly performs the full task locally and does not send logs, telemetry or prompts to another service. Local operation by itself is not a guarantee of privacy: device security, storage rules, updates and analytics still matter.

A strong case for cloud inference is access to more compute and memory. A remote service can run larger models, update them centrally and serve difficult tasks without using the phone's battery for all calculations. It can also support shared tools and large document collections. The costs include network dependence, operating expense and additional data-handling obligations.

A hybrid design uses local models for frequent or sensitive low-cost tasks and sends selected requests to a server when the user permits it. The difficult question is how the application decides when to escalate. That decision can introduce inconsistent behavior and privacy risks. No single deployment method is best for all users or tasks. The correct choice depends on quality requirements, data policy, connectivity and the real cost of operation.

14. Wider effects: access, energy and competition

Smaller models can make useful AI available where network connections are slow, expensive or unreliable. They can support offline translation, document classification, accessibility features and personal tools. Local processing can also reduce the amount of user data that must travel to a server. These are possible benefits, not automatic outcomes. Devices differ greatly in processing power, and a low-end phone may still lack the memory required by a compressed model.

Energy claims need special care. Moving work from a data center to a phone changes where energy is consumed. A local model may save network and server resources for some tasks, but repeated use can drain batteries and create heat. Hardware manufacturing and replacement also have environmental costs. To compare systems fairly, measure energy per completed task at the same quality and include the relevant parts of the service.

Compression can lower the barrier for small developers to deploy models. At the same time, access to high-quality training data, model licenses, specialized hardware and reliable evaluation still matters. A smaller file does not by itself create an open or affordable ecosystem. The distribution of benefits depends on product design, hardware access and market rules.

15. Eight lessons for a practical decision

  1. Define the real task and an acceptable error rate before selecting a model.
  2. Measure weight storage, peak memory, latency and energy separately.
  3. Use quantization to reduce number precision, and check the resulting quality.
  4. Use distillation when a smaller student can meet the task's needs.
  5. Protect sensitive numerical values instead of rounding every weight blindly.
  6. Test the complete runtime on the intended hardware and prompt lengths.
  7. Treat local execution as one privacy control, not a full privacy guarantee.
  8. Compare total cost per successful task, including errors and maintenance.

These lessons follow from the distinction between model-level improvements and application-level outcomes. A research result can identify a promising method, but it cannot replace a product test. Record the baseline, change one major factor at a time, and keep the failed cases for later review. This makes the choice explainable and reduces the risk of selecting a model because of a single impressive benchmark.

Knowledge check: five questions and answers

1. Why can a model file fit in storage but fail to run?

The device also needs memory for activations, the attention cache, software buffers and the operating system. File size alone does not measure peak working memory.

2. What is the difference between quantization and distillation?

Quantization represents model numbers with fewer bits. Distillation trains a smaller student model using information from a larger teacher.

3. Does 4-bit compression always make inference four times faster?

No. Fourfold is the theoretical raw weight-storage ratio relative to 16-bit weights. Speed depends on memory bandwidth, arithmetic support, cache use and software.

4. Why do GPTQ and AWQ treat weights differently?

Rounding errors have different effects. GPTQ uses layer-error information; AWQ uses activation information to protect important weight channels.

5. What would prove that a local model is suitable for an application?

A repeatable end-to-end test on the target device that meets quality, peak-memory, latency, energy and privacy requirements for representative tasks.
