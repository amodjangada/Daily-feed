Can an AI Model Truly Forget Your Data?

If a person withdraws their data, what would prove that a trained AI model no longer uses it?

Research checked 28 October 2026 · Both numerical examples are illustrative · Source dates listed below

Executive summary

A person can ask a service to delete a document. Removing the document from storage is straightforward to define, but removing its influence from a trained AI model is much harder. During training, many examples jointly change millions or billions of model parameters. There is usually no separate location that contains one person's contribution. Machine unlearning studies ways to make a model behave as if specified data had never been used. The strongest baseline is to train again without those examples. Researchers have proposed faster methods, including training models in isolated groups, certified removal for limited model classes, and approximate changes to large language models. Each method makes a different promise. Some reduce visible recall while leaving other traces; others preserve privacy but require substantial computation or reduce general accuracy. Recent benchmarks show why a single question-answer test cannot prove deletion. This guide explains the technical problem, the main algorithms, the evidence, and the difference between deleting a record, suppressing an answer, and changing a model. It also describes what a responsible deletion claim must measure and disclose.

1. The central question: what does forgetting mean?

Imagine a model that was trained on millions of documents. One author withdraws permission to use a particular document. A database administrator can remove the original file and stop future collection. Yet the trained model may still produce phrases, facts or associations that were influenced by that document. The author's request therefore has at least two technical parts: remove the source from systems that store it, and address the model that already learned from it.

Machine unlearning is the attempt to remove the influence of selected training data from a trained model. A rigorous goal is to make the resulting model statistically indistinguishable, within a defined guarantee, from a model trained from the beginning without that data. This is stronger than blocking a few questions. It also differs from deleting a conversation from an interface or clearing a search index. Those actions may be necessary, but neither alone changes model weights.

The practical question is which guarantee a system can provide, at what cost, and how an independent test can detect failure. The answer depends on the model, training process, threat model and deletion request. The research includes strong methods for restricted models and promising approximations for large networks. It does not establish one universal delete button for every deployed language model. [1] [3]

2. The vocabulary: data, weights, influence and proof

A training example is one unit of data used to adjust a model. A training set is the collection of examples. A model's weights are numerical values updated during learning. A gradient estimates how changing a weight would change the training error. Modern neural networks use many gradient updates, often with examples mixed into batches. This makes it difficult to assign a clean part of a weight to one person.

The forget set contains examples that must be removed. The retain set contains examples that remain authorized. Exact retraining trains a new model on the retain set under a specified procedure. Approximate unlearning changes an existing model to imitate the outcome without repeating all training. Certified removal gives a mathematical bound on how different the removed-data model can be from an appropriate retraining reference.

Memorization is the retention of details that can sometimes be reproduced. Generalization is learning patterns useful on new inputs. These are not cleanly separable in every case. If a document says that a historical event happened, a model may learn that fact from many sources. Removing one source does not necessarily make the model forget the fact. A good deletion specification must identify which data, which use and which observable behavior it covers. [2] [5]

3. How the research problem developed

Early machine-learning systems were often trained on smaller structured datasets. A developer could sometimes rebuild a model after removing one record. As models grew, repeated training became expensive, and users began to expect greater control over their data. Research turned deletion into an algorithmic problem: can a model support efficient removal requests while keeping useful performance?

Ginart and colleagues studied efficient deletion in machine learning in 2019. Their work proposed a formal approach and algorithms for k-means clustering, a method that groups similar records. They reported large speed gains for their specific setting. This result did not imply that the same guarantee was available for all neural networks. Bourtoule and colleagues introduced SISA training, which changes the original training process to limit how widely each example can affect a collection of models. [1] [2]

Guo and colleagues developed certified removal for linear classifiers in 2020. Later, language-model research tested faster ways to suppress selected knowledge. A 2023 study focused on material from the Harry Potter books. The 2024 TOFU and MUSE benchmarks asked a harder question: do the modified models behave like models that never saw the target data, and do they retain useful skills? The sequence of papers matters. Researchers moved from making deletion efficient in defined settings to testing how broad the claim can be for very large models. [3] [6] [7]

4. Why deleting a file does not reverse training

During neural-network training, a program reads batches of examples, calculates an error and adjusts weights. One example may influence a weight that is later changed by thousands of other examples. Its effect can spread through layers and interact with other patterns. The final weights do not normally include a readable ledger saying which bytes came from which record.

Suppose a model learned to complete a phrase because it appeared in several sources. Removing one source from the dataset changes the training history. It does not identify a unique group of weights to erase. Reversing one recorded gradient update is also not enough. Later updates were computed using the already changed model, so the training path itself depended on earlier states. Random batch order, dropout and optimizer state add further complications.

There are two separate security questions. First, can an observer cause the model to reproduce private text? Second, can an observer infer that a particular record was in the training data, even if the exact text is not reproduced? These are called extraction and membership-inference risks. Carlini and colleagues demonstrated extraction of memorized sequences from GPT-2 in a 2021 security study. That result establishes a real failure mode for the studied model, while leaving the risk for any other model to be measured separately. [4]

5. The strongest reference: train without the data

For a defined dataset and training procedure, the natural reference is a fresh model trained on the retain set alone. If the training algorithm is randomized, exact unlearning concerns the distribution of possible outcomes, rather than forcing two runs to have identical numerical weights. This is an important distinction: even two ordinary runs on the same data can end with different weights.

Full retraining gives a clear technical benchmark, provided the unwanted data is absent from all relevant inputs. That includes pretraining data, later fine-tuning sets and any training pipeline that can introduce the data again. A new model might still know a public fact through other permitted sources. Therefore, the presence of a fact in an answer does not automatically prove that a particular deleted source remained in training.

The difficulty is cost. Large language models can take substantial computing resources to train. If a service receives many deletion requests, restarting a full training run for every request is usually impractical. Research tries to avoid this expense without silently weakening the promise. A trustworthy system should state whether it uses exact retraining, a formal approximation or a behavior-level suppression method. These approaches are not interchangeable. [1] [7]

6. Method one: design training for future deletion

SISA stands for Sharded, Isolated, Sliced and Aggregated training. A shard is a separate group of training records. A system trains a model on each shard and combines their predictions. When a record must be removed, the system can retrain only the model whose shard contained that record. The other models did not see it. Slicing divides a shard's training sequence into stages and saves checkpoints, so retraining can restart before the affected stage. [2]

This changes the problem before it arises. Instead of asking a single monolithic model to forget one example, the system limits that example's influence by design. The method requires careful control of data assignment, checkpoint storage and aggregation. It also assumes isolation is real: shared pretraining, cross-shard features or later fine-tuning can create influence outside the named shard.

There is a trade-off. Each model sees less data, so its predictions may be weaker. Aggregating models can recover some performance, but not always. The original study reported speed improvements on several datasets, with accuracy trade-offs that depended on task complexity. It would be misleading to apply those measured speedups directly to a modern foundation model without a new experiment. SISA is most useful as a lesson in system design: future removal becomes easier when the training process records and limits where data can have an effect.

7. Method two: prove a bound on removal

Certified removal asks for a mathematical guarantee. In simplified terms, an observer should find it very difficult, under a specified statistical test, to distinguish the unlearned model from one trained without the removed examples. The guarantee is expressed using assumptions about the learning algorithm, data and permitted deviation. It is not a general promise that every possible question will produce a particular answer.

Guo and colleagues studied this problem for linear classifiers. They used techniques that approximate the parameter change caused by removing examples, then added carefully chosen randomness to meet their certified-removal definition. Their paper describes conditions in which this can be more efficient than retraining. [3]

Why does the model class matter? For some convex learning problems, the objective has useful mathematical structure. It can be possible to bound the difference between a corrected model and a retrained model. Large deep networks have more complex optimization behavior and many possible solutions. The same proof does not transfer automatically. When a company says that removal is certified, the next questions are: certified under which assumptions, for which data unit, and against which attacker? A limited but clear proof is more informative than an undefined promise of complete forgetting.

8. Method three: approximate changes to language models

Many practical proposals change an already trained language model with a short fine-tuning process. They may teach the model to avoid target text, alter next-token probabilities or reduce its preference for answers associated with the forget set. These methods are attractive because they can cost far less than rebuilding a large model. They also create a risk: visible refusal or poor recall on a narrow test can look like successful removal even when the model retains other traces.

Eldan and Russinovich published a 2023 preprint describing approximate unlearning of Harry Potter material from a seven-billion-parameter language model. They reported a relatively short fine-tuning process and limited changes on selected general benchmarks. This was evidence for a specific method and evaluation, not a proof that all information was removed. [5]

Later evaluations made the limitations clearer. TOFU uses fictional author profiles so researchers can know exactly which information was introduced and then targeted for removal. Its authors found that their tested baselines did not achieve effective unlearning across the full benchmark. MUSE added broader checks, including privacy leakage, utility and repeated requests. These findings suggest that the difficulty lies partly in evaluation: a method can succeed at one visible behavior and fail at another. [6] [7]

9. Diagram: three routes from a deletion request

Start by defining the request. A person might ask to remove one file, all of their training records, or a class of private facts. These are different scopes. The system then needs a reliable map from each data item to every dataset, model checkpoint, fine-tune and retrieval index that used it. Without this map, even a good unlearning algorithm may target the wrong model.

After the chosen method runs, evaluation should compare the new model with an appropriate reference. The test should include prompts not used to tune the method. It should measure whether the target material is still exposed, whether the model can still perform unrelated tasks and whether future updates reintroduce the data. An operator should also keep evidence of which request, dataset version and model version were processed.

10. What must a serious evaluation measure?

The MUSE researchers organized evaluation around six properties. Three matter directly to data owners: whether the model reproduces exact text, whether it retains target knowledge, and whether it leaks information about the presence of target data in training. Three matter to deployers: whether unrelated capabilities remain useful, whether the method scales to large forget sets, and whether it can handle successive deletion requests. [7]

A good test also separates a model's behavior from a user-interface filter. A filter can stop some responses while leaving underlying weights unchanged. That may reduce immediate exposure, but it does not establish unlearning. Similarly, a failed extraction attempt is weak evidence if the test covers only a few prompts. The evaluator must state the attack budget, the prompts tried and the remaining uncertainty.

11. What the experiments establish—and what they do not

The early deletion papers provide constructive results in controlled settings. Ginart and colleagues developed efficient algorithms for clustering; Guo and colleagues showed certified removal for linear classifiers. Bourtoule and colleagues demonstrated that isolating training data can reduce retraining costs on their tested datasets. These are meaningful advances because they specify algorithms and measurable objectives. They are not proofs of easy deletion from every deployed model. [1] [2] [3]

The language-model studies expose a wider gap. The Carlini extraction work showed that a trained model can reveal exact sequences. The Eldan and Russinovich method showed that targeted fine-tuning can reduce recall on selected evaluations. TOFU and MUSE then demonstrated that many proposed approaches do not meet several desired properties at once. MUSE's results were based on selected seven-billion-parameter models, datasets and eight algorithms. They should not be presented as a measurement of every future method or commercial system. [4] [5] [6] [7]

Across these studies, the strongest general conclusion is about verification. A deletion claim must identify a reference model and a testable threat model. The evidence does not support a universal statement that unlearning always works, or that it can never work. Different model classes and guarantees require different conclusions.

12. Worked example one: why isolation changes cost

Illustrative calculation, not a research benchmark. A small organization trains an ensemble of ten independent models, each on one tenth of a dataset. Assume every component takes 10 compute-hours to train, and all components can run in parallel or in sequence. The full ensemble costs 100 component compute-hours. If one record appears in only one shard, and the operator can restart that shard from a suitable checkpoint, the retraining work might be close to 10 compute-hours rather than 100.

Under these simplified assumptions, the work ratio is 100 ÷ 10 = 10. That is a tenfold reduction in component training work. It is not necessarily a tenfold reduction in wall-clock time: parallel hardware, checkpoint loading, testing, aggregation and deployment also take time. If the same person has records in six shards, more components may need retraining. If every component used a common pretrained model that included the deleted record, the assumed isolation does not hold.

The example explains the appeal of SISA without claiming a measured production speedup. Its value comes from an architectural choice made before training. It also shows why data lineage matters. A system that cannot identify which shards received a record cannot reliably use the method. The original SISA study reports its own results and trade-offs for specific experiments. [2]

13. Worked example two: a model that appears to forget

Illustrative test, with invented counts. Suppose a model answers 90 of 100 target questions correctly before an unlearning procedure. After editing, it answers only 5 correctly. On that test, target-question accuracy fell from 90% to 5%. It would be tempting to declare success. But suppose a second, previously unseen set of prompts still extracts 30 of 100 target details, and performance on unrelated questions falls from 85% to 60%.

The procedure has reduced one visible form of recall. It has not established that the model behaves as if the data had never been included. It may have learned to refuse familiar wording, while other prompts recover the information. It has also damaged general performance. A stronger evaluation would compare against a retain-only reference model, test multiple extraction methods and report confidence intervals. If membership inference is a concern, that attack must be tested separately.

The arithmetic is simple; the inference is not. A change in one benchmark score is evidence about that benchmark. It is not a complete privacy guarantee. This is why TOFU uses several measures and MUSE examines privacy leakage, utility, scale and repeated requests together. [6] [7]

14. Competing approaches and their strongest arguments

One view gives priority to strict guarantees. If a user requests deletion, a model should be demonstrably equivalent to one that never trained on the removed records, subject to a clear formal definition. This position treats unverified approximation as too weak for sensitive data. Its strongest argument is accountability: users should not need to trust a developer's claim that a few test prompts stopped working. Its difficulty is cost and the limited range of models for which proofs are available.

A second view favors practical risk reduction. Large deployed models may be too expensive to rebuild after each request. Targeted fine-tuning, output safeguards, source deletion and careful monitoring can reduce exposure while research improves. Its strongest argument is feasibility: some protection delivered promptly can be useful. Its weakness is that a reduction in visible exposure can be mistaken for removal of training influence. A service must avoid using the same word, “deleted,” for both outcomes.

A third approach is architectural. It designs data stores, training jobs and model versions so that deletion can be tracked and affected components rebuilt. This may require more storage, engineering work and sometimes lower model accuracy. Yet it can reduce future uncertainty. These positions are not mutually exclusive. The correct choice depends on data sensitivity, legal duties, training scale and the strength of evidence required. [2] [3] [7]

15. Deletion is a system process, not only an algorithm

A real service can hold data in raw uploads, backups, caches, analytics stores, retrieval databases, training snapshots, fine-tuning sets and model checkpoints. A request that affects only one location may leave copies elsewhere. The operator needs an inventory of data flows, retention rules, model versions and authorized uses. The technical model-unlearning step is only one part of this work.

There is also a legal distinction. Privacy and copyright rules differ by jurisdiction, purpose and exception. A right to erase a stored record does not always translate into a specified technical method for every derived model. Conversely, a company should not assume that deleting a database row automatically settles every obligation. This guide explains technical evidence and does not offer a legal determination for any specific service.

A defensible process should record the scope of the request, verify the requester's authority, identify the relevant model versions, perform the available deletion operations and document limitations. The report to the requester should distinguish verified source removal, model retraining, approximate suppression and any unresolved copies. Independent testing is valuable when the data is sensitive or the claims are consequential. Such records support auditability without requiring public disclosure of private content.

16. Wider effects and the research still needed

Unlearning affects how organizations plan AI systems. It can influence data licensing, vendor contracts, training design, storage costs, and whether a model can be maintained after a dataset's terms change. A firm that buys access to data for a limited period may need to know what happens when that period ends. A healthcare provider may need stronger proof than a public product-catalog application. The same technical label can hide very different risk levels.

Research questions remain open. How can an evaluator distinguish true removal from a model that has learned to avoid a known test? Can strong guarantees scale to large generative models without expensive retraining? How should a system handle knowledge that appears in both removed and retained sources? How can it process repeated requests without gradually destroying unrelated capability? And how should a provider prove the result without exposing the private data used in the test?

These are engineering and measurement questions, as well as policy questions. The evidence so far supports careful claims tied to specific methods. A useful future standard would state the data scope, the algorithm, the reference baseline, the threat model, the evaluation results and the residual uncertainty. Until then, the phrase “the AI forgot” should be treated as a claim that needs a definition and evidence, rather than as a simple property of a product.

Key lessons

  1. Deleting source files and deleting learned influence are separate operations.
  2. Exact retraining on the retain set provides a strong reference for unlearning claims.
  3. Model weights do not normally identify one person's contribution as a removable block.
  4. SISA reduces future deletion work by isolating training influence from the start.
  5. Certified removal is meaningful only with its model assumptions and formal bound.
  6. Approximate language-model edits can reduce recall without proving full removal.
  7. Tests must examine extraction, membership leakage, unrelated utility and repeat requests.
  8. An audit needs data lineage, model-version records and honest disclosure of limits.

Five knowledge-check questions

1. Why is deleting a training file insufficient?

The file may already have changed model weights. Removing stored bytes prevents one future use but does not reverse earlier gradient updates.

2. What is the difference between exact retraining and approximate unlearning?

Exact retraining rebuilds a model using the retain set. Approximate unlearning changes an existing model to imitate the desired outcome, with guarantees that depend on the method.

3. How does SISA reduce retraining work?

It isolates data into shards and saves training stages. A request can trigger rebuilding only the affected components when isolation assumptions hold.

4. Why can a model fail an unlearning audit despite refusing target questions?

Other prompts may still recover target data, membership attacks may reveal training participation, or unrelated performance may have collapsed.

5. What should a deletion report disclose?

It should name the targeted data and model versions, the removal method, the reference baseline, the tests performed, their results and any remaining uncertainty.
