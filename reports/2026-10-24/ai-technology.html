Why Fast AI Depends on Moving Less Data

What happens inside a computer when a language model answers, and why can memory traffic matter more than raw computing power?

Evidence-led learning report · 24 October 2026 · Worked numbers are illustrative unless a source is named.

Executive summary

A language model can have billions of numerical weights and still generate text one token at a time. This creates a surprising engineering problem. The processor can often perform calculations faster than it can bring the needed numbers from memory. During the first reading of a prompt, many calculations can run together. During later token generation, a small request may spend much of its time moving model weights and past attention data. This is why a faster chip does not always produce a proportionally faster answer. Researchers have developed several methods to reduce wasted data movement. FlashAttention changes how attention is calculated without approximating the standard result. PagedAttention manages the growing memory used for earlier tokens. Grouped-query attention stores fewer key and value vectors. Quantization stores weights in fewer bits. Batching lets many requests share the cost of reading model weights. These methods solve different limits, and their gains depend on hardware, model design, input length and traffic. The useful lesson is to measure both response delay and completed work, then find the actual limit before selecting an optimization.

1. Background: from language to hardware

A large language model, or LLM, is a program trained to predict the next piece of a sequence. A token is a unit of text processed by the model. A token can be a whole word, part of a word, or punctuation. The model uses parameters, also called weights: stored numbers that control its calculations. Training adjusts these weights. Inference uses the trained weights to answer a new request. This report is about inference, although several of the same memory ideas also affect training.

The 2017 Transformer paper introduced an architecture based on attention, a method that lets positions in a sequence use information from other positions. Its parallel processing helped make large-scale language systems practical. Modern generative models often use a decoder-style Transformer. A decoder predicts one next token, adds that token to the sequence, and repeats. That repeated process is important: even if a chip has enormous arithmetic capacity, the model must still manage dependencies between successive output tokens. [1]

A GPU, or graphics processing unit, can perform many mathematical operations in parallel. It is well suited to multiplying large arrays of numbers, called matrices. Yet a GPU has several levels of memory. Small on-chip memory is fast and scarce. High-bandwidth memory, or HBM, is much larger but takes more time and energy to access. Data movement across these levels can limit how fast the model runs. The FlashAttention research made this issue explicit: an algorithm should account for memory reads and writes, not only the number of arithmetic operations. [2]

This topic differs from the question of whether an AI system makes a good decision. A model can be accurate but slow. It can also be fast but wrong. Hardware efficiency and answer quality are separate measures. They interact when an optimization changes numerical precision or the model itself.

2. What the machine must hold

Consider three main kinds of data. First are the model weights. A model with many parameters needs space for those numbers. Second are temporary values produced while the model works through its layers. These are often called activations. Third are saved attention values from earlier tokens, commonly called the key-value cache, or KV cache. The cache lets the model reuse earlier work instead of calculating the full history again for every new token.

These kinds of data have different life cycles. Weights normally stay fixed during inference and can be shared across requests using the same model. Activations are produced and consumed as calculations progress. The KV cache belongs to a request or a shareable prefix and usually grows as the request becomes longer. A serving system must make room for all three. It also needs working space for kernels, buffers and other runtime tasks. A model that appears to fit based only on weight size can fail when long prompts or many users add KV-cache demand.

The CPU usually handles request routing, scheduling and other control tasks, while GPUs perform much of the model calculation. Moving data between CPU memory and GPU memory may add delay. Splitting one model across several GPUs can provide more capacity, but communication between GPUs becomes another possible limit. There is no single number called “GPU speed” that predicts every workload.

Think of an engineering system in terms of capacity and flow. Capacity asks how much data can be held. Flow asks how many bytes can be transferred each second. Two GPUs may have similar capacity but different bandwidth. Another pair may have similar bandwidth but different compute capability. A successful design must satisfy all three: enough capacity, enough data movement, and enough arithmetic performance.

3. Why reading a prompt differs from writing an answer

Inference has two broad phases. During prefill, the model processes the input prompt and creates attention information for its tokens. Many positions can be processed in parallel, subject to causal attention rules: a position may use earlier positions but not future ones. This often creates large matrix operations that use a GPU efficiently. A long prompt can still take considerable time, especially when attention or cache creation is expensive.

During decode, the model generates new tokens. For a standard autoregressive decoder, the next token depends on the tokens already generated. The system therefore repeats a model pass for each output token. With only one request in progress, some operations are small compared with the large matrix operations of prefill. The GPU may have spare arithmetic capacity while repeatedly loading weights and cache data. Decode is often described as memory-bandwidth-bound under these conditions. That description is a useful model, not a universal law.

Why is this distinction important to a user? A system can begin showing text quickly but generate the rest slowly. Another system may take longer before the first token appears but then produce text quickly. The first delay is often measured as time to first token (TTFT). The continuing rate is measured as tokens per second or time between output tokens. These measures reveal different limits. An average response time alone can hide them.

Longer outputs add more decode steps. Longer prompts add more prefill work and usually increase the cache that later decode steps must read. If a user asks for a short answer to a large document, prefill can dominate. If a user asks for a long response to a short question, decode may dominate. A service handling both kinds of requests must balance them rather than optimize only one.

4. Arithmetic speed, memory bandwidth and the roofline idea

A useful performance model compares the amount of computation with the amount of data moved. Arithmetic intensity means operations per byte transferred from a specified memory level. If an operation performs many calculations on each loaded byte, compute capacity may limit it. If it performs few calculations per byte, memory bandwidth may limit it. This is the central idea behind roofline-style performance analysis.

The simple lower-bound estimate for moving data is:

Transfer time ≥ bytes transferred ÷ effective memory bandwidth

This is a lower bound because the program also performs calculations, waits on dependencies, and pays scheduling and communication costs. Peak bandwidth printed on a hardware specification is not the same as effective bandwidth achieved by a particular program. A memory-bound operation may also become compute-bound when batching changes its data reuse.

For example, imagine a single decode step that must read a large weight array and does relatively little useful work per weight. Its time may depend strongly on the weight bytes that move. If the same weights are used for many requests together, each weight read can support more arithmetic. That raises arithmetic intensity and can improve total throughput. However, larger batches also need more cache memory and may make an individual request wait longer. A high throughput figure can therefore coexist with poor response delay.

There are further complications. Model layers include different operations, not one uniform matrix multiplication. Attention must read past key and value vectors. Small operations and communication overhead can dominate at some sizes. Modern GPUs also have caches, specialized matrix units and different data formats. The roofline idea is a guide for locating a limit; it does not replace a real performance profile.

5. FlashAttention: do the same math with fewer memory transfers

Attention uses query, key and value vectors. A query represents what a token seeks. Keys represent candidate matches, and values carry information to combine. Standard scaled dot-product attention calculates similarity scores between queries and keys, applies a normalization called softmax, and uses the resulting weights to combine values. For a sequence of length N, the full score table can have N × N entries. Its size grows quickly with sequence length.

A simple implementation may write a large score matrix to HBM, read it for softmax, and read or write it again for the weighted sum. Those transfers cost time and memory. FlashAttention, published at NeurIPS 2022, reorganized the exact attention calculation into smaller blocks, or tiles. It keeps more intermediate work in fast on-chip memory and avoids materializing the full attention matrix in HBM. It uses an online normalization method so blocks can be combined without changing the intended attention result, apart from ordinary floating-point differences. [2]

The distinction matters. FlashAttention is not simply “approximate attention.” Its main contribution is an input-output-aware way to calculate exact attention. The paper reported speed improvements on selected workloads, but those numbers depend on sequence length, GPU and comparison implementation. FlashAttention-2 later changed how work was divided across GPU thread groups and reduced some non-matrix arithmetic. The 2024 paper reported about twice the speed of FlashAttention on its evaluated attention workloads, with performance approaching more of the hardware's matrix-compute capacity. [3]

Reducing memory traffic does not make every stage linear in time. Standard full attention still involves interactions between many token pairs during prefill, so its arithmetic work grows roughly quadratically with sequence length. FlashAttention can reduce the memory needed for the intermediate attention matrix without removing that full mathematical work. Claims about “linear memory” and “quadratic computation” refer to different resources. Mixing them produces misleading comparisons.

Long-context systems benefit from this distinction. A program can run out of memory before it reaches its arithmetic limit. Better memory handling can make longer sequences possible. Yet a larger context still costs time and may reduce the number of users served at once. More available context also does not guarantee that a model uses distant information correctly.

6. KV cache: the hidden cost of remembering earlier tokens

During generation, the model needs information about earlier tokens. Recalculating all their keys and values at every step would waste work. Instead, a decoder commonly saves those vectors in a KV cache. Each new token adds more vectors. The amount depends on the number of layers, key-value heads, head dimension, token count and bytes per stored number. If many requests are active, their caches compete for GPU memory.

The cache can waste space even before it becomes full. One request may stop after a short answer. Another may continue for thousands of tokens. If the system reserves a large continuous block for each possible request, unused space remains trapped. If it repeatedly allocates and frees variable-size blocks, memory can become fragmented: free bytes exist, but they are difficult to use efficiently. This is a memory-management problem familiar from operating systems.

The 2023 PagedAttention paper adapted the idea of virtual-memory paging to attention caches. Instead of requiring one continuous physical region for a sequence, the system stores KV data in blocks and keeps a mapping from logical positions to physical blocks. The authors built the vLLM serving system around this approach. They reported 2–4 times higher throughput than selected earlier serving systems at comparable latency in their experiments. That is a result for the tested systems and conditions, not a universal multiplier for all deployments. [4]

Paging has an extra benefit when requests share a prefix. Several questions may begin with the same system instructions or document. A serving system can sometimes share the stored prefix rather than duplicate all its KV data. Sharing requires careful handling of later changes and references. A cache is also an internal performance structure; it is not a guarantee of persistent user memory across separate conversations.

Cache design introduces a trade-off between capacity and scheduling complexity. Smaller blocks may reduce wasted space but increase metadata and lookup work. Larger blocks can be simpler but leave more unused space at the ends of sequences. Real implementations choose block sizes and kernels together. The best choice depends on the request mix and the GPU architecture.

7. Four complementary ways to reduce inference cost

Method A: quantize the weights

Quantization represents numbers with fewer bits. A common reference format uses 16 bits per weight. A 4-bit representation needs roughly one quarter as many raw weight bits, before scales, metadata and other overhead. Fewer bytes can reduce memory capacity and bandwidth needs. But arithmetic kernels must support the format efficiently, and converting or dequantizing values can add work. Some layers or outlier values are more sensitive to reduced precision than others.

The 2023 GPTQ/OPTQ research showed that large Transformer weights could be compressed to low bit widths with limited accuracy loss on evaluated models and tests. It also reported speed gains using suitable kernels. These findings support quantization as a practical technique, but a quality result on one benchmark does not establish acceptable performance for every language, task or safety-sensitive use. [5]

Method B: use fewer KV heads

In ordinary multi-head attention, several attention heads have separate key and value representations. Multi-query attention shares a key-value head across many query heads, reducing cache data. Grouped-query attention, or GQA, uses an intermediate number of KV heads. It can keep much of the speed benefit while preserving more capacity than the most aggressive sharing design. The EMNLP 2023 GQA paper reported quality close to multi-head attention with speed comparable to multi-query attention for its evaluated models. This is a model-architecture decision and can require further training; it is not always a switch that a server operator can enable after deployment. [6]

Method C: batch requests

Batching processes several requests together. It can improve reuse of weights and raise GPU utilization. A static batch waits for a group to finish together, which wastes capacity when some responses end early. The Orca research proposed scheduling at the level of each generation iteration, allowing the active group to change between token steps. This idea underlies what is often called continuous batching. The paper showed large improvements over its comparison system in a specified experiment; that result should not be applied to an unrelated server without measurement. [7]

Method D: improve attention kernels and cache layout

FlashAttention reduces unnecessary intermediate transfers inside attention. PagedAttention reduces waste and duplication in the cache used by active requests. These methods target different parts of the same service. They can complement quantization and batching, although each combination must be supported by the actual model and software stack.

8. Worked example: weight traffic and a lower bound

Illustrative calculation, not a benchmark. Assume a decoder has 7 billion parameters. If every parameter is stored in 16 bits, its raw weights occupy 7 billion × 2 bytes = 14 billion bytes, or about 14 GB in decimal units. Ignore embeddings that may be tied, scale factors, runtime buffers and all other overhead for this first estimate. Suppose the system must read roughly all those weight bytes for one token and has an effective memory bandwidth of 1 TB per second.

14 GB ÷ 1,000 GB/s = 0.014 seconds = 14 milliseconds

This gives a rough transfer-only lower bound of 14 milliseconds for that assumed pass, or about 71 such passes per second if nothing else mattered. It is not a prediction of observed output speed. Real performance also depends on cache reuse, arithmetic, attention, kernels, synchronization, output processing and other traffic. Some operations may be compute-bound. A different memory layout may cause more or fewer bytes to move.

Now imagine a 4-bit weight representation. Raw weight storage becomes 7 billion × 0.5 byte = 3.5 GB. Under the same unrealistic assumption of reading only those bytes, the transfer lower bound falls to 3.5 milliseconds. The theoretical ratio is four to one. Actual speedup can be much smaller because quantization adds scale information and decoding work, and the bottleneck may shift elsewhere. It can also fail to improve speed if the hardware lacks efficient low-bit kernels.

The exercise shows why fewer bytes are useful but also why advertised bit-width ratios should not be sold as guaranteed speed ratios. If the original workload was already compute-bound, reducing weight traffic may have little effect. If the service processes many requests in a batch, the same weights can support several token calculations, so per-request arithmetic and cache traffic matter more.

9. Worked example: why a long conversation consumes memory

Illustrative calculation. Consider a hypothetical decoder with 32 layers, 8 key-value heads per layer, 128 numbers per head, and 2 bytes per number. Every stored token needs both a key vector and a value vector. The approximate KV-cache space per token is therefore:

2 × 32 layers × 8 KV heads × 128 values × 2 bytes = 131,072 bytes ≈ 128 KiB per token

For a 4,096-token sequence, this is 536,870,912 bytes, or 512 MiB, for one request's KV cache under the stated assumptions. Ten such requests would require about 5 GiB just for this cache data. This excludes weights, activations, allocator overhead and other runtime storage. Real models vary widely in layers, head count, head dimensions and cache precision.

If the same hypothetical model had 32 KV heads instead of 8, with other values unchanged, the cache would be four times larger. This illustrates the memory benefit of fewer KV heads. If a request grows from 4,096 to 8,192 tokens, its cache approximately doubles, assuming a simple full-history cache. That is why long contexts can reduce how many users fit on a GPU at once.

Paging does not change the number of useful key and value numbers in this formula. It reduces wasted allocation and can permit sharing. Quantizing the cache itself may reduce bytes per number but adds accuracy and kernel considerations. Sliding-window or other limited-context attention can change what must be retained, yet it also changes which past tokens are directly available. These are different engineering choices and should not be grouped into one “memory optimization” claim.

10. What the research establishes—and what it does not

There is strong published evidence that memory-aware implementations can improve particular Transformer workloads. The original Transformer established the broad architecture. FlashAttention and FlashAttention-2 demonstrated attention-kernel improvements on specified hardware. Orca demonstrated better scheduling for iterative generation. PagedAttention showed how cache management can raise serving throughput. GQA and GPTQ showed ways to reduce the data stored or moved while maintaining useful model quality on tested cases. Together, these papers explain why system design matters beyond the model's parameter count. [1] [2] [3] [4] [5] [6] [7]

The limits are equally important. A research paper usually compares selected models, workloads, GPUs and baseline software. Later libraries may already contain the technique being tested. Speedups from different papers cannot be multiplied together: the techniques can target overlapping limits, and removing one bottleneck exposes another. Throughput gains do not always imply lower time to first token. A method that saves memory can allow more simultaneous users while making a single user's response no faster.

Precision changes deserve separate quality checks. A compressed model may have similar average benchmark accuracy yet differ on rare inputs, numerical reasoning or languages with less training data. Quantization should therefore be evaluated against the actual tasks a service performs. For a safety-critical task, a small average difference may hide an unacceptable tail risk. Likewise, longer context capacity is not the same as reliable retrieval or reasoning over the whole context.

Claims about electricity and environmental impact require measured power and utilization. A faster model may use less energy for one task, but lower costs may increase total demand. Hardware manufacture, cooling and idle capacity also affect the full footprint. None of the speedup figures cited here directly measures a universal reduction in energy per correct answer. Such a claim would need separate evidence.

A careful benchmark should report model version, input and output lengths, concurrency, hardware, numerical format, software version and whether the model was already loaded. It should distinguish average from high-percentile latency and include an accuracy check. Without these details, “tokens per second” can compare different tasks and mislead buyers.

11. Competing approaches and real trade-offs

Use the largest capable model, or use a smaller efficient one?

One view is that a larger model is worth higher serving cost when it produces better answers on difficult tasks. A stronger model may need fewer retries or less human correction. Another view is that a smaller model, chosen for a narrow task, can provide a better balance of cost, speed and accuracy. Neither position wins without a task-specific comparison. The right unit is an accepted result, not just one generated token.

Optimize for one person's speed, or for total service capacity?

A personal assistant benefits from short delay before the first token and steady output. A busy public service may prioritize completed requests per second while meeting a latency target. Large batches can increase overall throughput but delay individual requests. A scheduler must decide how to allocate work when short and long requests compete. Fairness matters because a few very long jobs can otherwise harm everyone else's response time.

Buy more hardware, or improve software?

Adding GPUs can increase capacity and sometimes reduce queueing. It also adds equipment, operating and communication costs. Software changes such as better kernels, quantization and cache management can extract more useful work from existing hardware. Yet software tuning requires skilled engineering and can introduce maintenance risks. The best choice depends on whether the present limit is compute, memory, interconnect, scheduling or application quality.

These disagreements are practical rather than ideological. Each approach can be correct under a different workload. The strongest evaluation compares the full service against its actual demand pattern and a defined quality threshold.

12. Why this matters for products and society

For product teams, inference design affects what a user experiences. A writing assistant must begin responding promptly. A document-analysis tool may need to handle long inputs. A voice system needs low delay because pauses interrupt conversation. A background research task may accept slower responses in exchange for lower cost. These products should not use the same performance target simply because they all use a language model.

For businesses, memory efficiency affects capacity planning. A service can pay for powerful hardware but leave it underused because requests arrive in uneven patterns or caches consume the available memory. A good design measures the real distribution of prompt lengths, output lengths and simultaneous users. It then tests whether changing batch size, model precision or cache management improves service-level goals. A service-level goal is a measurable target, such as the share of requests that begin responding within a stated time.

For researchers, memory-aware algorithms make larger experiments and longer sequences more accessible. They can also change which model designs are attractive. If a particular architecture requires far less KV-cache storage, it may support more concurrent users at a given memory capacity. But the scientific value of an optimization includes reproducible comparisons and clear disclosure of any change in model behavior.

For the wider economy, more efficient inference can lower the resources needed to serve each request and expand access. It can also increase total use. That means efficiency is necessary for affordable systems but does not, by itself, settle questions about total electricity demand, data-center expansion or access to computing resources. Those questions require separate market and energy evidence.

13. Eight key lessons worth remembering

  1. Inference is not training. It uses learned weights to process new inputs and produce outputs.
  2. Memory capacity and bandwidth differ. Capacity determines what fits; bandwidth helps determine how fast data can move.
  3. Prefill and decode behave differently. Input processing often uses more parallel work; one-request decoding may be limited by memory traffic.
  4. Attention has several costs. Its arithmetic work, intermediate storage and KV-cache traffic must be considered separately.
  5. FlashAttention reduces unnecessary transfers. It does not remove all quadratic computation from standard full attention.
  6. PagedAttention improves cache allocation. It does not make useful KV data disappear.
  7. Quantization, GQA and batching solve different limits. Their benefits depend on the model and hardware.
  8. Benchmark the whole task. Report latency, throughput, accuracy and operating conditions together.

14. Knowledge check: five questions with answers

Question 1. Why can a GPU with high arithmetic speed still generate text slowly?

Answer: It may spend much of its time loading model weights or past attention data. If memory transfer is the limiting step, unused arithmetic capacity cannot remove that delay.

Question 2. What changes between prefill and decode?

Answer: Prefill processes the input sequence and builds its attention state. Decode repeatedly generates new tokens, normally one token per request at each step, using the earlier state.

Question 3. Does FlashAttention make full attention linear in computation?

Answer: No. It reduces intermediate memory transfers and storage for the exact attention calculation. Standard full attention still involves many token-pair interactions.

Question 4. Why can batching improve throughput but hurt response time?

Answer: Several requests can reuse the same loaded weights and keep the GPU busy. However, requests may wait for a batch slot or compete for memory and scheduling time.

Question 5. What must be checked before using 4-bit weights in production?

Answer: Measure quality on the actual task, confirm efficient low-bit kernels on the hardware, check real memory savings, and compare latency and throughput at realistic traffic levels.
