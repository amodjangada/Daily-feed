When Can an AI Agent Be Trusted to Act?

What must be checked before software can act for a person?

BackgroundHow it worksEvidence and trade-offsReal-world casesCompeting viewsKey lessonsKnowledge checkSources and further reading

Executive summary

AI systems now do more than answer questions. Some can read files, choose steps, use software and send results. These are commonly called agents. Their main value is that they can finish a chain of work without constant human input. Their main risk is that a wrong answer can become a wrong action. A sound design limits what the agent may do, checks its work and asks for consent when a step could cause harm. The correct test is not whether an AI produces a fluent explanation. It is whether the full task succeeds, whether the result can be checked and whether mistakes can be found and fixed. Risk rises when an agent can send money, change records or speak for someone. The NIST AI Risk Management Framework sets out four linked functions: govern, map, measure and manage. These can guide how a team tests AI tools before and after launch.

Background→ Method→ Evidence→ Cases→ Lessons

Background

Earlier computer programs followed set instructions. Statistical models later learned patterns from examples. Large language models can now generate plans and commands in plain language. Joining a model to tools turns an answer system into an actor. This shift matters because text errors and action errors have different costs.

How it works

  1. Define the job and the boundary. State what counts as success and which actions require approval.
  2. Give the agent only the data and tool access it needs. Separate reading from writing or sending.
  3. Require a plan, records of each tool call and checks against source documents.
  4. Test ordinary cases, rare cases and attempts to insert false instructions.
  5. Record outcomes in use, review failures and suspend high-risk actions when checks fail.

Evidence and trade-offs

A model may state a plausible answer even when its evidence is weak. If that answer controls a tool, the result may be costly. Adding a second model review can help but two models may share the same blind spot. Independent checks using rules, logs and source records are stronger.

A reliable benchmark should measure final task outcomes, error severity, human review time and recovery cost. An agent that finishes 90% of tasks may still be unfit for payment approval if the remaining errors involve large transfers.

Recent work on AI use in professional software makes this question current. A tool that reads contracts may be useful for finding terms but should not silently agree to new terms.

Real-world cases

  1. A contract assistant finds a renewal date. A person can verify the date in the source clause. The assistant may draft a reminder, but sending a binding notice needs approval.
  2. A help-desk agent may suggest a refund based on policy. A rule should check purchase amount, time limit and the allowed refund cap before money moves.

Competing views

Supporters argue that guarded agents can reduce routine work and allow staff to focus on hard cases.

Critics argue that changing inputs and complex tools make real failures hard to predict, especially when the agent acts at scale.

Key lessons

  1. Task success matters more than fluent output.
  2. Access rights should be as narrow as possible.
  3. Check against sources, not only a second AI.
  4. High-cost actions need explicit approval.
  5. Measure failures after launch, not just before.

Knowledge check

1. What makes an agent different from a chatbot?

It can use tools and take steps in the outside world.

2. Why can two model checks fail?

They may repeat the same mistake.

3. Name a strong independent check.

A rule that compares an action with the source record.

4. What does least access mean?

Give only the rights needed for the task.

5. What should testing measure?

Task outcome, errors, their cost and recovery.
