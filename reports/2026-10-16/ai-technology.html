When Can We Trust an AI Agent?

How do AI agents plan and act, and what evidence tells us when they are reliable enough to use?

Independent research study · Sources and evidence inside · Examples marked illustrative

Executive summary

An AI agent combines a language model with tools, a process for choosing actions, and feedback from the world. The important change from a chatbot is that the system may search files, execute code, update records, or send a message. This gives it practical value and new ways to fail. Reliable performance depends on the task, the tools, the permission limits, and the quality of evaluation. METR's 2026 time-horizon work shows why a performance claim is incomplete without the test set and its scoring rules. Anthropic's field research shows that real users grant different levels of autonomy in different contexts, while security work by OpenAI and OWASP highlights prompt injection and excessive permissions. A single impressive demonstration cannot establish safe performance in daily use. This report explains the agent loop, tool interfaces, testing methods, compounding error, human oversight, and deployment trade-offs. It also works through a numerical reliability example. The central lesson is that trust must be specific: a given agent, completing a given task, with defined tools and consequences, under measured conditions.

1. Background: from chat to action

A language model predicts useful next text from a prompt and the context supplied with it. It can explain a plan without doing any part of the plan. An agent adds a way to select and use external tools. Examples include searching a document store, running code, or editing a calendar. A workflow normally uses a fixed order of stages; an agent can select and repeat stages as it observes results. The boundary is not absolute because many products combine both approaches. Anthropic's December 2024 engineering guide argues that teams should start with simple, testable patterns and add autonomy only where it solves a real problem. [1]

Tool use was part of wider attempts to make models useful outside chat. In March 2025 OpenAI introduced tools for web search, file search, and computer use through its Responses API, with tracing and orchestration features for developers. Tracing means recording which decisions and tool calls happened during a run. These records matter because a final answer can appear sound even if the route to that answer involved unnecessary actions, skipped checks, or a lucky guess. [2]

The key distinction is authority. A text answer is advice. A tool call may change data. If an agent deletes a file or sends money to the wrong account, later correction may be impossible. Reliability must therefore include whether the system chose an authorized action, not merely whether its final message looked plausible.

2. How the agent loop works

Start with a defined goal. The system sees task instructions, relevant files, tool descriptions, and any saved state. It proposes a next action, such as checking an invoice against a purchase order. A tool processes that action and returns a result. The model reads the result, updates its working view, and decides whether to continue, ask for clarification, stop, or submit a final output. This is a feedback loop: information from one step changes the next decision. [1]

A tool is an interface to another system. A search tool may return text; a payment tool may move funds. The model should receive only permissions needed for the job. A useful separation is read, draft, approve, and execute. An agent can read an invoice, draft a payment request, and calculate a total without gaining permission to submit the payment. Only after a human checks the request should the final tool become available.

The agent also needs state: what has been completed, what remains, and which results are verified. Without state, an agent may repeat the same action. With poorly designed state, it can treat an earlier error as established fact. A reliable implementation records the origin and confidence of key facts and makes each operation traceable. State is not proof that the recorded content is correct.

Why tool results can be dangerous

External pages and documents are *data*. They may contain malicious text that tells the agent to ignore its task or send private information elsewhere. This is called prompt injection. The danger arises when the agent treats lower-trust source text as an instruction that overrides the user's goal or tool limits. OpenAI's March 2026 research explains why attacks can resemble ordinary social engineering and why filtering suspicious phrases alone is not enough. OWASP identifies excessive agency as a separate risk: access that is too broad can turn an ordinary model error into a damaging action. [4][5]

3. What does reliable performance mean?

Reliable is not one number. Task success asks whether the desired outcome happened. Process correctness asks whether the steps were allowed and justified. Safety asks whether harmful actions occurred. Efficiency asks how much time, computation, and review were required. Recovery asks what happened after an error. An evaluation must state how these dimensions were measured.

Suppose an agent correctly identifies a customer refund but sends the amount twice. A study scoring only the classification would call the first stage a success. A study scoring the full business outcome would call the run a failure. The definition of success is part of the result, not an administrative detail.

Researchers commonly use a set of tasks with known outcomes, often called a benchmark. The evaluator runs many attempts and calculates a success rate. Benchmarks are useful for comparing systems under fixed conditions. They do not automatically measure rare events, changing software screens, new document types, or attacks from real users. The system must also be tested on tasks that resemble the work it will actually perform.

METR's January 2026 Time Horizon 1.1 update revised its software-task evaluation from 170 to 228 tasks and increased the number of tasks estimated to take humans eight hours or more from 14 to 31. Some older tasks were removed or changed. METR cautioned that estimated model horizons shift when the task mix and evaluation method change. That is why apparent progress cannot be interpreted without checking the test itself. [3]

The time horizon is an estimate of the duration of a human task that an agent can complete at a stated success probability in a particular benchmark. It does not mean the agent can run without error for that many hours on any task. For example, a model can succeed on a long coding assignment but make a simple error when a website changes its layout. Neither observation cancels the other.

4. Worked example: small errors become large risks

Imagine a hypothetical service agent that completes an eight-step account update. Assume it has a 98% chance of performing each step correctly, that errors are independent, and that all eight steps must be correct. The probability of full success is 0.98⁸ = approximately 85.1%. This means about 15 of 100 complete runs could contain at least one failed step under these artificial assumptions. The result shows why a good step score does not guarantee a good workflow score.

Now add a verified check after the fourth step that detects and safely corrects most errors. That could improve end-to-end success, but the final effect depends on the check's own error rate, what failures it can see, and whether its corrections create new problems. Repeating the same model's reasoning is not automatically an independent check. A better control may be a programmatic rule, an external source of truth, or human review of high-impact actions.

In real workflows the errors are rarely independent. A mistaken customer ID at step two may cause wrong invoices, wrong totals, and wrong messages later. This is a correlated failure: one underlying mistake creates several bad outcomes. Product testing should trace failure chains and report both individual-step errors and completed-run errors.

5. What the latest evidence can and cannot tell us

Anthropic analyzed millions of human-agent interactions in work published in February 2026. In the longest-running Claude Code sessions it examined, time operating before stopping rose from under 25 minutes to over 45 minutes during a three-month period. This is an observation about a particular product and set of users. It does not establish that all those sessions succeeded, that users were equally safe, or that every agent has the same ability. [6]

Research on coding productivity provides another caution. In early 2025, a METR experiment found experienced open-source developers took longer with the tools available at that time. In February 2026 METR said later data were too biased by participant selection to support a firm estimate of current productivity impact, despite some signs of improvement. The honest conclusion is that measured capability and workplace value are related but different. [7]

A well-run evaluation includes representative tasks, adversarial cases, variations in input quality, and several attempts per case. It measures how often the agent asks for help when the task is uncertain. It separately reports the cost of false actions and missed actions. A service agent that never makes a bad payment because it refuses every request is safe on one narrow measure, but it is not useful.

6. Competing design choices

Some teams prefer structured workflows because they can test every branch and restrict what a model controls. Others support more open-ended agents when work is too varied for a fixed script. These positions reflect different tasks and risk levels rather than a dispute about whether AI is useful. For a regulated billing process, the predictable workflow may be better. For a low-risk research task, an adaptive agent can handle unexpected sources with less code. [1][5]

A separate disagreement concerns how much human review is useful. Too little review permits costly errors. Review at every trivial step consumes time and may become a formality. A more defensible design asks for approval where an action is hard to reverse, has legal effect, exposes private material, or exceeds an agreed value limit. Anthropic's April 2026 governance paper emphasizes meaningful human control, clear actions, and limits on the agent's authority. [8]

7. Why this matters beyond software

AI agents change how work is divided between people and systems. Workers may spend less time gathering routine information and more time defining goals, judging exceptions, and checking results. Businesses may gain speed but also become dependent on vendors, tool availability, data quality, and a new kind of audit process. A small team can automate much more work; the same team can also multiply errors if it grants broad permissions without controls.

The central business question is therefore not 'Can the demo finish the task?' It is 'Can the complete system produce a correct, authorized result at a useful cost, across the conditions we expect, and recover when it fails?' A sound deployment logs actions, protects credentials, uses least privilege, stores clear approval records, tests old failures after changes, and has a simple way to stop execution. These are ordinary engineering disciplines applied to systems that choose their own next steps.

There is genuine uncertainty about how rapidly agents will improve and how well benchmark scores will translate into general workplace performance. That uncertainty justifies close measurement, not automatic rejection or uncritical adoption. The sensible choice is to increase autonomy as evidence from the actual workflow becomes stronger.

Key lessons

  1. An agent uses a model and tools in a feedback loop; a chatbot answer alone is not an executed task.
  2. Tool authority matters as much as model accuracy.
  3. A workflow success rate can be far below individual-step accuracy.
  4. Benchmarks are conditional on task design, scoring, and runtime setup.
  5. Prompt injection begins when untrusted source text is treated as an instruction.
  6. Read-only access, scoped tools, approval gates, and logs reduce consequences of errors.
  7. Human oversight should concentrate on costly and irreversible actions.
  8. Test actual business outcomes, not only attractive model responses.

Knowledge check

Answer each question before you open the explanation.

Why can a 98%-accurate step still result in unreliable work?

When many steps must all succeed, their probabilities compound. Under an independent eight-step illustration, 0.98⁸ ≈ 85.1%. Real errors can be correlated, so the figure is not a measured agent success rate.

What is the difference between a workflow and an agent?

A workflow has a mostly predefined path; an agent can choose the next tool action based on observed results. Real systems often combine both.

Why is a successful benchmark not sufficient for deployment?

The test may exclude rare errors, malicious material, actual permissions, changing tools, and business costs. The production task may differ from the benchmark.

What is prompt injection?

It is an attempt to make an agent obey instructions inside lower-trust content such as web pages or retrieved files rather than the authorized task instructions.

When should an action require human approval?

A useful rule is to require review before actions that are expensive, sensitive, legally meaningful, or hard to reverse. The exact thresholds depend on context.
