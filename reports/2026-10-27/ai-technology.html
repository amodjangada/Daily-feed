Why AI Agents Fail at Multi-Step Tasks

What makes a tool-using AI reliable when it must change real systems, handle errors and prove that work is complete?

Research checked 27 October 2026 · Numerical calculation and publication workflow are illustrative

Executive summary

An AI agent does more than write an answer. It selects tools, reads their results, changes records and decides whether a task is complete. This creates new failure points. A model may understand a request yet choose the wrong tool, omit a required step, misread a returned value, break a business rule or announce success before the system has changed. Research on ReAct and Toolformer shows why linking language models to tools can improve performance. Research on WebArena, SWE-bench and τ-bench shows how much harder it is to finish real, multi-step work. Security studies add another problem: tool output can contain instructions that the agent must treat as untrusted data. This guide follows a task from a user's goal to a verified final state. It explains planning, tool calls, state management, permissions, recovery and evaluation. It separates useful design rules from findings established by experiments. The practical conclusion is that reliable agents need observable outcomes, constrained actions and a way to recover from errors. Fluent text alone is not evidence that work is done.

1. The central question: what makes an agent different?

A language model can answer a question without changing anything outside the conversation. An agent is a system that uses a model to choose actions in an environment. The environment might be a browser, an email account, a database, a code repository or a set of software tools. An agent observes a state, decides what to do, acts, receives a result and may repeat the process. Its work is judged partly by what changed in the external system.

A tool call is a structured request to a program, such as “read this file” or “create this calendar event.” The tool returns data or an error. The model may then use the result to decide its next step. A workflow is the ordered set of actions needed to meet the user's goal. A side effect is an external change: a message sent, a file committed, a payment initiated or a record edited.

These terms matter because a convincing explanation and a completed action are different outputs. An agent can correctly describe how to update a record while never updating it. It can also make a real change while describing that change incorrectly. Evaluation must examine both behavior and the resulting state.

The key design question is therefore not whether a model can generate a plausible plan. It is whether the complete system can perform the authorized task, detect failure, preserve correct work and prove the final outcome. That question is separate from the retrieval and preference-training topics covered in earlier Daily Feed editions.

2. From scripted automation to language-guided action

Traditional automation uses explicit rules. A developer writes a sequence: read a form, check a field, send an approved request, then verify the response. This is predictable when the inputs and software interfaces remain stable. It becomes costly when users describe goals in many ways or when a task requires interpreting unfamiliar information.

Language models offer a flexible interface. They can translate a request into a plan and choose among available tools. ReAct, introduced in a 2022 preprint and published at ICLR 2023, studied an alternating pattern of reasoning and acting. The model could use observations from an environment to revise its next action. The paper reported improvements on selected question-answering and interactive decision tasks; those results belong to its experimental settings, not to every modern agent. [1]

Toolformer, published at NeurIPS 2023, examined how a model can learn to decide when to call external application programming interfaces. Its experiments included tools for arithmetic, search, translation and other functions. It showed that tool use can improve some tasks without replacing the model's general language ability. [2]

The important historical shift was from generating a single answer to selecting a sequence of operations. That shift also changed the standard of proof. For a written response, a reader can inspect the text. For an agent, the final database or file system must be inspected too.

3. Define success before the first tool call

A vague goal such as “organize these orders” is hard to test. A precise goal names the records, required changes, constraints and acceptable end state. An agent should convert the request into preconditions, actions and postconditions. Preconditions describe what must be true before an operation. Postconditions describe what must be true after it finishes.

Suppose a task requires creating five documents in a repository. The postcondition is not “the assistant wrote five descriptions.” It is “five complete files exist at the requested paths, each has the required structure, and a readback confirms the content.” If a public website is also required, a separate postcondition must check that the public URLs serve the files. A commit alone does not prove deployment.

Clear postconditions let the agent stop correctly. Without them, it may continue changing files after success or finish early because a tool returned a friendly message. A validator is a separate check of the expected result. It can be a test suite, a file readback, a database query or a human approval step.

Good requirements also identify forbidden actions. An agent may be allowed to draft an email but not send it. It may be allowed to create a new file but not overwrite an existing complete one. These are not minor preferences. They define the agent's authority and the scope of a correct result.

4. Stage one: plan around dependencies

A multi-step task has dependencies. One step may need information produced by an earlier step. A file cannot be updated safely until its current version is known. A purchase should not proceed until the item and price are confirmed. A useful plan states which actions depend on which others and which can run independently.

A dependency graph shows this order. Its nodes are operations; its arrows indicate that one result is required before another. An agent should not confuse a list of desired outcomes with an executable order. It should also allow the plan to change when a tool returns new facts.

Long plans are fragile when they assume that every intermediate step will work. A robust agent makes the next decision using observed state, not only the original prediction. ReAct provided an early research demonstration of interleaving reasoning and environment observations. That does not mean exposing private internal reasoning is required for reliable products. An explicit action log and a clear state record can serve operational needs without disclosing hidden model processes. [1]

Planning is especially important when actions are irreversible. Reading a record is usually low risk. Deleting it, transferring funds or sending a message can have lasting effects. The plan should place authorization and validation before high-impact actions and should prefer reversible steps when the outcome is uncertain.

5. Stage two: choose the correct tool and arguments

An agent needs a reliable description of each tool. The description should state what the tool does, the required fields, valid values, permission limits and possible errors. A schema defines the structure of a request. It may require a repository name, file path, exact version identifier and full replacement content.

Structured arguments reduce ambiguity, but a valid request can still be wrong. A path may point to the wrong date. An email address may be syntactically valid but belong to the wrong person. A quantity may use the wrong unit. The agent must check the meaning of the arguments against the user's goal, not only their format.

Tools can also fail before any action occurs. A request may time out, hit a rate limit or lack permission. A response can be partial. An error can occur after a side effect has happened, leaving the caller unsure whether to retry. This is why every consequential write needs a way to inspect the resulting state.

Toolformer explored the benefit of teaching models when to use tools, but it did not solve every issue of authority, state or correctness. [2] In production, the tool interface should help the model make safe choices: descriptive names, narrow capabilities, explicit types, useful errors and read operations for verification. Broad “do anything” tools make mistakes harder to limit.

6. Stage three: observe state instead of trusting a narrative

The state of a system is the set of facts that currently matter: which files exist, which messages were sent, what values are stored, and which steps have already completed. An agent can carry a summary of that state in its working context, but summaries can become stale or incomplete. The external system is the source of truth for its own records.

A read-after-write check is simple: perform a write, then independently read the target and compare it with the expected value. This can catch a failed request, a wrong path, an unexpected transformation or a stale version. For public publishing, the repository and the public site are different states. Both may need separate checks.

For complex tasks, the agent should maintain a small execution ledger: step name, target, attempted action, observed result, verification status and error if any. This ledger need not be a sophisticated database. A structured log is often enough to prevent repeating completed work after an interruption.

One danger is treating the model's earlier statement as evidence. If it wrote “file created,” that statement may be wrong. The actual file content, commit identifier and public response are stronger evidence. The difference is central to agent reliability: the language model proposes actions, while observations establish what happened.

The loop matters because a successful tool invocation is not always a successful task. A tool may accept a request while a later deployment fails. Conversely, a timeout may occur after a write has succeeded. Reading state before retrying avoids accidental duplication.

In a real system, the loop also needs an authorization boundary. The agent may propose a high-impact action, but a separate permission rule or human approval can decide whether that action is allowed. The model's confidence is not an adequate substitute for that boundary.

8. Why long tasks fail more often

A task with several steps can fail even if each step is usually reliable. If every step succeeds with probability p and the failures are independent, the chance of completing all n steps is pn. This is a simplified calculation, not a measured property of any particular model.

Illustrative calculation: suppose a workflow has ten necessary steps and each succeeds 95% of the time, independently. The full-run success rate is 0.9510, or about 59.9%. If the step success rate rises to 99%, full-run success becomes 0.9910, or about 90.4%. Small differences in per-step quality can matter greatly across long sequences.

Real failures are rarely independent. A wrong early assumption may corrupt every later step. A missing permission can stop all writes. A bad document can affect several decisions. The calculation is useful because it shows why good single-turn performance does not guarantee reliable multi-step execution; it is not a prediction of observed agent success.

There are also two different notions of success. Task success asks whether the final state is correct. Process compliance asks whether the agent followed the permitted steps and restrictions. An agent could reach a correct final value after using an unauthorized tool. That outcome should still fail the compliance check.

9. What realistic benchmarks found

Researchers have built benchmarks that test agents inside environments rather than asking them to answer isolated questions. WebArena, first released as a 2023 preprint, provides functional websites and tasks that require navigating and changing information. In the paper's original evaluation, the best GPT-4-based baseline completed 14.41% of tasks, compared with 78.24% for humans under the reported setup. These are historical baseline results, not current performance estimates. [3]

SWE-bench, presented at ICLR 2024, uses 2,294 real software issues from twelve Python repositories. Agents must modify code to resolve the issues. Its original paper reported a 1.96% resolution rate for the best tested baseline, Claude 2. Later systems and benchmark variants should not be compared to that number without matching evaluation conditions. [4]

AgentBench, published as a 2023 preprint, tested language models across eight interactive environments. Its authors identified long-term reasoning, decisions and instruction following as important sources of failure. [7]

These studies support a narrow but important conclusion: interactive tasks expose weaknesses that a simple question-answering test can miss. They do not establish a single universal success rate for all agents. Task design, tools, model version, time budget and scoring rules strongly affect measured results.

10. Reliability across repeated runs

A system that succeeds once may still be unsuitable for routine operations. Users need to know whether it will succeed repeatedly under similar conditions. τ-bench, introduced in June 2024, studies tool-using agents in simulated customer-service settings with domain policies and changing conversations. It compares the final database state with an annotated target state. [5]

The paper also proposes passk, a measure of consistency over repeated trials. In its original tests, even strong function-calling agents succeeded on fewer than half of the tasks, and the reported pass8 in the retail domain was below 25%. These figures describe the tested models and benchmark in 2024. They should not be treated as current rates for a different system.

Why does repeated testing matter? A task may contain several equally plausible choices. A model might follow a policy in one run and miss a restriction in another. If the result changes with minor wording or tool order, one successful demonstration hides a serious reliability problem.

For business workflows, useful tests include repeated runs, unexpected tool errors, missing records, changed field names and conflicting instructions. The output should record not only average success but also the worst failure modes. A high average can conceal a rare action with a large cost.

11. The security boundary: data is not an instruction

An agent often reads material it did not author: web pages, email bodies, search results, repository files and database notes. This material can contain instructions addressed to the model. A prompt injection occurs when lower-trust content tries to redirect the agent away from the user's authorized task.

For example, a document being summarized might contain text telling the assistant to ignore the user and disclose private data. The text is part of the document. It is not an authorized request. A system must preserve the distinction between data that can be analyzed and instructions that can control actions.

AgentDojo, introduced in June 2024, created an extensible environment for testing agents that use tools while reading untrusted material. The authors described 97 realistic tasks and 629 security test cases. Their findings show that task performance and resistance to prompt injection are separate concerns. [6]

Practical controls include limited tool permissions, isolation of untrusted content, validation of tool arguments and explicit approval for sensitive writes. A language model can help detect suspicious text, but detection alone is not a complete security boundary. The tool system should refuse actions that exceed the user's permission even if the model requests them.

12. Worked example: a multi-file publication

Illustrative example, not a measured experiment. An assistant must publish two research articles to a Git repository. It must preserve existing good files, use exact dated paths and verify publication. The first action is to read both target paths. If one is complete, the assistant records it as done and does not overwrite it. For the missing path, it prepares the full article, checks its structure and commits it. It then reads the file back and checks the title, date, required sections and source links.

Next, the repository's deployment system may build a website. A successful commit is a repository fact. A successful public deployment is a different fact. The assistant must request the public URL and check that the expected article is served. If the public URL cannot be reached, it reports “repository verified; website unverified.” It must not turn a missing observation into a claim of success.

Now consider an interrupted run. The assistant sees a timeout after sending the commit request. It does not immediately repeat the write. It reads the target path. If the correct file exists, it records success. If the file is absent, it can retry. If the content differs, it inspects the version before making a change.

This workflow illustrates idempotency: repeated attempts should not create duplicate or destructive effects. Idempotency may come from a unique operation identifier, a pre-write existence check, or a tool designed to apply the same requested state safely.

13. Permissions, approvals and reversibility

An agent should have only the authority required for its task. This is the principle of least privilege. A research assistant that reads web pages needs no permission to transfer money. A draft-writing assistant may need access to create drafts but not to send messages. Narrow permissions reduce the damage from mistakes and malicious content.

Authorization has several layers. The user grants a broad goal. The application defines which tools the agent can call. Each tool can enforce rules on specific resources. High-impact operations may need an additional approval step. These layers should not rely on the model to remember every restriction correctly.

Reversibility also matters. Reading a record is reversible because it changes nothing. Creating a draft can usually be undone. Sending an email or deleting a remote resource may be difficult to reverse. When a task offers several valid routes, the agent should prefer the route that can be checked and corrected before an irreversible action.

A related concept is transactionality: a group of operations either completes together or leaves the system in a known state. Many web workflows do not support full transactions. In those cases, the agent needs a recovery plan for partial completion. The plan should state which successful changes to keep, which to reverse, and which require human review.

14. How to evaluate a real agent

A useful evaluation starts with representative tasks and ground-truth end states. The evaluator should inspect actual records, files or application behavior. It should also test whether the agent respected permission limits and whether it reported uncertainty correctly. A pleasant final message is not a reliable scoring method.

Measure at least four dimensions. First, end-state correctness: did the requested changes occur? Second, rule compliance: were forbidden actions avoided? Third, recovery: did the agent handle timeouts, stale versions and partial work? Fourth, evidence quality: does the report of completion match what independent checks show?

Task suites should include both ordinary and adverse cases. An ordinary case tests a complete, well-formed request. An adverse case may contain a missing file, a changed interface, conflicting data or an injected instruction in retrieved content. Benchmarks such as WebArena, SWE-bench, τ-bench and AgentDojo address different parts of this space. No single one is a complete certification of reliability. [3] [4] [5] [6]

Tests should also preserve version details. A score without the model, tools, data snapshot, policy and test method is hard to interpret. When an agent changes, rerun the same tests and add new cases for failures found in use.

15. Competing designs: flexible agents or fixed workflows?

There are two serious approaches to building useful automation. One gives a language model broad control over tool selection and planning. It adapts to unfamiliar tasks and can interpret natural requests. Its cost is variability: the sequence may differ across runs, and unexpected actions are harder to predict.

The other approach uses a fixed workflow with a language model only at selected points. A program handles order, validation, permissions and retries. The model interprets ambiguous text or drafts content inside those boundaries. This approach can be easier to test and audit, but it may require engineering work for each new task.

A third practical choice combines them. The model proposes a plan or content; deterministic code checks schemas, permissions and end states. The model can revise its proposal when a check fails. This hybrid design still needs careful tests. A validator can be incomplete, and an incorrect rule can reject good work or approve bad work.

The best design depends on task risk and variability. A low-risk research summary can tolerate more flexible exploration. A payment, account change or customer communication requires tighter controls. Research on tool use establishes useful methods, while realistic benchmarks warn against assuming that a model's general language skill makes every multi-step workflow dependable.

16. Practical implications and open questions

Agents may reduce the time spent moving information between systems. They can read requests, draft documents, inspect repositories, prepare changes and report results. The largest gains often come from repetitive work that has clear success conditions and reliable interfaces. But an agent can also create extra review work if it makes changes that are hard to inspect.

Teams should distinguish a pilot from dependable operation. A pilot asks whether the task can be completed at all. Dependable operation asks whether it works across many cases, with controlled failures, accurate status reports and acceptable cost. A useful pilot should record every attempted action and every final-state check.

Open research questions remain. How should agents represent long-running state without losing important details? How can they learn to stop when evidence is insufficient? Which tests predict performance outside the benchmark? How should systems handle multiple agents changing the same resource? What level of independent verification is enough for different risks?

These questions cannot be answered by model accuracy alone. The quality of tools, access controls, observability and task design all matter. The safest general rule is to treat an agent as a system that proposes and performs actions under constraints, then require external evidence before declaring that its work is complete.

Key lessons

  1. Specify an observable final state before taking action.
  2. Treat the tool response as evidence to inspect, not a guarantee of task success.
  3. Read the target state before overwriting or retrying a write.
  4. Keep a small execution record so interrupted tasks can resume.
  5. Use narrow tool permissions and separate approval for high-impact actions.
  6. Treat retrieved documents and tool outputs as untrusted data.
  7. Measure full-task success and rule compliance, not just individual correct steps.
  8. Test repeated runs and adverse conditions; one successful demo is insufficient.
  9. Compare benchmark results only when models, tasks and scoring match.
  10. Report repository, deployment and public availability as separate states.

Knowledge check: questions and answers

1. Why can a ten-step workflow fail often even when each step is usually correct?

Answer: Errors can accumulate across required steps. Under an illustrative independent 95% per-step success assumption, ten-step success is about 59.9%. Correlated errors can make real outcomes better or worse.

2. What is the difference between a successful tool call and a successful task?

Answer: A tool call reports that an operation was accepted or executed. Task success requires checking the requested final state and the rules that constrain it.

3. Why should an agent read a file after a commit?

Answer: The readback checks the actual target path and content. It catches wrong paths, failed writes, partial data and mistaken success claims.

4. What makes prompt injection different from a normal instruction?

Answer: Prompt injection is an attempt by lower-trust material, such as a page or tool result, to control the agent. The authorized user and application permissions define what the agent may do.

5. What does τ-bench add to simple task-success tests?

Answer: It evaluates tool-using agents against final database states and studies consistency across repeated trials, including whether agents follow domain policies.
