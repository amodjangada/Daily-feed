Can an AI Assistant Remember the Right Things—and Forget the Rest?

A guide to persistent AI memory, from fact extraction and retrieval to changing information, privacy and deletion.

Research checked 3 November 2026 · Preprints are labeled · Numeric examples are illustrative

Executive summary

A chat assistant can use a long conversation while it remains in the active context. That does not give it reliable memory across weeks or months. Persistent memory is a separate system. It must decide what to store, how to represent it, when to retrieve it, how to handle changes, and when to delete it. Research shows that a larger context window alone does not solve this task. Benchmarks such as LoCoMo and LongMemEval test recall across sessions, time, updates and abstention. Newer work tests multi-party conversations and user-requested forgetting. The results show gains from memory design, but also gaps in temporal reasoning and retrieval. Memory can improve personal relevance and reduce repeated work. It can also preserve errors, expose sensitive details, or apply an old preference after it has changed. This guide explains the main design steps and the evidence behind them. It compares full-history context with external memory, and summaries with structured records. The central finding is practical: useful AI memory needs source links, time stamps, user control and tested deletion. A system that remembers everything is not a safe or reliable system.

1. The central question

Imagine that a person tells an assistant in January that they prefer short answers. In March, they ask for a detailed report. In June, they change jobs and ask the assistant to stop using an old project name. A useful assistant must recall the first preference when it helps, ignore it when the task needs depth, and replace the old project detail. It must also keep private information away from other users.

This guide asks: How should an AI assistant decide what to remember, use, update and forget? This is a system-design problem. It involves language models, databases, search, time, permissions and user choice. A larger prompt does not solve it. We must assess the full memory lifecycle.

2. Define the terms

Context is information available to a model for one response. A context window is the model's input limit. Persistent memory is information kept outside the active conversation for use in later sessions. Retrieval is the process of finding stored information for a new request.

Episodic memory records an event, such as a meeting decision. Semantic memory stores a fact or rule. Profile memory stores a pattern about a person, such as a stated preference. Working memory holds information needed for the current task. These are design labels. They do not mean that an AI system has a human brain or human experience.

Provenance means where a fact came from. Temporal metadata records when it was stated and when it was valid. A knowledge update changes an earlier record after new information arrives. Deletion removes data from relevant stores and copies. Hiding one search result is not full deletion.

3. From context to persistent memory

Early chat systems added recent turns to each new prompt. This works for short conversations. It becomes costly as history grows. A model may also miss a detail even when it remains in the input. Long-context research has shown that a large window does not ensure equal use of every passage.

In October 2023, Packer and colleagues introduced MemGPT. It moved information between a limited active context and external storage. In March 2024, Zhong and colleagues presented MemoryBank at AAAI. It extracted and updated selected information from earlier dialogue. These papers helped define memory as a separate system, not just a larger prompt [1] [2].

4. Why context is not memory

Context is temporary input. Memory is a managed record that can survive the current request. A summary of earlier chats is one memory method. It can omit detail, merge two people, or turn a temporary plan into a lasting preference. It can also become stale if no process checks it against later statements.

Persistent memory adds selection, storage, search, relevance, update and deletion. Each stage can fail. A correct fact that is never retrieved has no effect. A wrong fact that is retrieved can make a fluent answer less accurate. A model's trained parameters are also different from an external memory store. Removing a database entry does not remove the same information from logs, backups or model weights.

5. Step 1: select what to store

A memory system should not store every sentence. Many statements are one-time requests, jokes, guesses or temporary details. A selection rule can ask whether a fact is likely to help later, how often it matters, how costly it would be to forget, how sensitive it is, and whether the user agreed to retain it.

Repetition can signal value, but it is not enough. A person may repeat an old address for one delivery. A single statement may matter more if it changes a deadline. The system should label each record as a fact, preference, plan, event, or inference. It should also separate a user's statement from an independently verified record.

One request for short answers does not prove a permanent preference. If the request appears across many tasks, the system may propose a general setting. It should retain the source events and mark the general rule as an inference. The user must be able to inspect or correct it.

6. Step 2: choose a representation

A raw transcript preserves exact wording, but it is large and may contain details that do not need to be retained. A summary is compact, but may remove dates and uncertainty. A structured record can store a subject, fact, source, time, confidence, sensitivity label and access rule. A graph can link people, projects and events.

MemGPT used separate memory levels and controlled movement between them [1]. MemoryBank used a process to extract and update information from dialogue [2]. A product can combine these methods: keep a short recent history, store selected events, and place stable facts in structured records.

7. Step 3: index and retrieve

Keyword search helps when a user repeats a name or phrase. Semantic search uses vector representations to find passages with related meaning. Hybrid search combines both. A date filter can restrict results to the relevant period. A graph can connect facts that use different words but refer to the same person or project.

Retrieval is not proof. A search system ranks records by a match score. It does not prove that the top result is correct or current. A question about a meeting decision may need the date, participants, decision and later changes. One similar sentence may not contain the full answer.

LongMemEval tested indexing, retrieval and reading. Its authors reported a large accuracy decline on long histories. They also showed that session decomposition, better index keys and time-aware queries improved results on their benchmark [4]. This shows that retrieval design matters. It does not prove that one search method is best for every task.

8. Step 4: update facts over time

Personal facts change. A user can change a role, address, deadline or preference. A memory system should not keep two conflicting records and choose one at random. It should preserve the history and mark which record is current. It must also distinguish a correction from a new event. "I moved last week" updates an address. "I will move next week" is a plan.

A structured record can include when the statement was made, when it became true, when it stopped being true, and when the system stored it. These dates answer different questions. A user asking what address was used in April needs the historical version. A user asking where to send a parcel today needs the current version.

EverMemBench, posted on 1 February 2026, tests multi-party conversations, interleaved topics and changing knowledge. Its authors report that temporal reasoning remains difficult [7]. A time stamp alone cannot resolve every conflict. The system needs version rules, source priority and a way to ask when an update is unclear.

9. Step 5: decide when memory applies

A memory can be accurate and still be irrelevant. A preference for short answers may help with a simple question. It may harm a request for a detailed report. A remembered food preference may matter for a meal plan, but not for an unrelated topic. The system needs a relevance test before it inserts personal facts into the current context.

EverMemBench separates memory awareness from simple recall. It reports that similarity-based retrieval can miss a relevant fact when a new question uses indirect wording [7]. This is why tests must include real tasks, not only direct questions such as "What is my favourite colour?"

10. Step 6: answer with evidence

When a system uses memory, it should keep the retrieved record available while it writes. The answer should reflect the source and date. If the record is old or uncertain, say so. If two records conflict, explain the conflict or ask for a correction. Do not silently combine incompatible facts.

A memory system also needs an abstention rule. If it cannot find a reliable record, it should say that it does not have the information. It should not guess about the user. LongMemEval includes abstention as a tested ability [4]. A confident answer about a person's past can be more harmful than a clear statement that the record is missing.

11. Step 7: make forgetting real

A user may withdraw consent, correct a sensitive fact or ask a system to stop using an old detail. A deletion control should identify where the information exists. It may appear in a transcript, summary, vector index, graph, cache, audit log or backup. Removing only the first record may leave copies that can still be retrieved.

Wang and colleagues studied privacy risks in LLM agent memory. Their preprint, first submitted on 17 February 2025 and revised on 3 June 2025, tested a black-box memory extraction attack on two representative agents [8]. The study does not measure risk for every product. It shows that stored private information can be a target.

In October 2026, Zhang and colleagues introduced MemCut, a preprint that tests user-requested forgetting. It contains 456 hand-designed secrets with annotated evidence trails. The authors report that removing the main disclosure reduced ordinary retrieval more than it reduced recovery from related records [9]. Deletion must cover indirect traces, not only the first sentence.

A policy should state what is deleted, what may remain for legal or security reasons, how long backups persist, and when deletion is complete. A system should stop creating new copies while a request is processed.

12. Diagram: a memory lifecycle

The diagram shows why memory is not one database query. The system must make several decisions and keep enough information to explain them. A memory entry without a source and date is hard to audit. A deletion process without a list of linked copies is hard to verify. Retrieval without access checks can expose information to the wrong person.

14. What early system studies tested

MemGPT tested a hierarchical design for long documents and multi-session chat. It showed how a controller can move information between active context and external storage [1]. This can extend useful history beyond one prompt. It also adds a failure point: the controller may not retrieve the needed record.

MemoryBank tested a process that extracts and updates information from dialogue. It reported experiments with a system called SiliconFriend, including real user dialogues and simulated conversations [2]. These results support the idea that stored information can improve continuity. But a companion scenario does not cover every work task, and simulated users do not represent all real behavior.

15. What long-term benchmarks reveal

Maharana and colleagues introduced LoCoMo in a preprint on 27 February 2024. It contains long conversations across multiple sessions and tests question answering, event summarisation and multimodal dialogue. The authors reported that models struggled with long-range time and cause relationships. Long-context and retrieval methods improved some results but remained below human performance in their tests [3]. The paper appeared in the ACL 2024 proceedings in August 2024.

Wu and colleagues introduced LongMemEval on 14 October 2024. It tests information extraction, cross-session reasoning, time reasoning, knowledge updates and abstention. The authors reported a marked decline in accuracy as histories grew. They also tested changes to indexing and time-aware retrieval [4]. These tests separate different failure types: missing a fact, choosing the wrong date, ignoring a correction, or answering without evidence.

Benchmarks use controlled conversations and fixed questions. They do not reproduce every feature of a real relationship or workplace. They do provide repeatable tests for comparing systems. A product team should add its own tests, with consent and strong data protection.

16. What newer research adds

Tavakoli and colleagues posted BEAM and the LIGHT framework on 31 October 2025. BEAM contains 100 generated conversations and 2,000 validated questions. Some histories reach 10 million tokens. LIGHT combines long-term episodic memory, recent working memory and a scratchpad for important facts. The authors reported average gains of 3.5% to 12.69% over their strongest baselines, depending on the model [5]. These are benchmark results, not a product guarantee.

EverMemBench, posted on 1 February 2026, adds multi-party and multi-group conversations. It tests detailed recall, memory awareness and user-profile understanding. The authors report that time reasoning and multi-hop reasoning remain difficult [7]. Real memory often involves several people discussing one project across channels. The system must know who said what and whether a later statement changes an earlier one.

A March 2026 preprint by Liu and colleagues studies memory-augmented routing between small and large models. On selected LoCoMo and LongMemEval tests, it reports lower inference cost when a smaller model can retrieve relevant user facts. It also finds that retrieval can help simple factual questions and hurt some time-based tasks [6]. Memory can reduce cost only when it returns useful records.

17. Privacy and deletion evidence

Memory may contain health details, finances, work plans, family events or location information. A user may not expect a casual statement to remain available months later. A system should store only what is needed for a clear purpose. It should separate private memory from shared workspace records and apply access rules to both.

The MEXTRA study by Wang and colleagues tested attacks that attempt to extract private information from LLM agent memory. It was first submitted on 17 February 2025 and revised on 3 June 2025. The authors reported successful extraction in their tests of two agents [8]. This does not mean all systems have the same risk. It shows that memory access is a security boundary.

MemCut tracks secrets through related conversation turns and checks whether a system can still recover them after deletion. The authors report that removing the main disclosure did not remove every path to recovery [9]. A product must map each fact to its source, summaries, indexes and backups. It should test that deletion works through normal retrieval and known residual paths.

18. Two illustrative examples

Example 1: a changing preference

Illustrative data only. A user says in January: "Send project updates on Friday." In April, the user says: "The team now reviews updates on Wednesday." A simple store may keep both sentences and retrieve the one that best matches a new question. That can return the wrong day.

A structured store can mark the first schedule as valid until April, then mark the new schedule as current. Both records remain available for historical questions. If the user later says the change was temporary, the system should add an end date or ask for the current schedule. Updates need time rules, source priority and a way to handle uncertainty.

Example 2: retrieval cost

Illustrative data only. Assume an assistant has 10,000 stored turns. A full-history prompt sends all 10,000 turns to the model. A memory pipeline selects 40 candidates, reranks 10, then sends 5 records to the model. The final model input is 99.95% smaller by turn count: 5 instead of 10,000.

This is not a measured cost saving. The pipeline still pays for indexing, storage, search and updates. It may also miss the right turn. If the five records are wrong, the smaller input can produce a wrong answer more efficiently. Evaluation must include answer quality, latency, storage and retrieval failures.

19. Competing views on memory design

Full context or external memory? Full context is simple and preserves original wording. It avoids some early summary errors. But it becomes costly and can exceed the model's ability to use the input. External memory reduces active input and supports updates, but adds retrieval errors. A hybrid can use recent context and selected records.

Summary or structured facts? A summary is compact and keeps the broad story. It may lose exact dates and sources. Structured facts support filtering and versioning, but extraction can be wrong. Use a summary for broad context and structured records for precise tasks.

Store more or less? More data may improve recall, but it raises privacy risk and can add irrelevant results. Less data protects users, but may remove facts needed for continuity. Selective storage with clear purpose, retention time and user control is the stronger default.

Human-like memory or engineered records? A simple story about human forgetting does not make an AI system safe. A database needs explicit source, time, permission and deletion rules. These rules are easier to inspect and test.

20. Limits of the evidence

Most public benchmarks use constructed conversations and fixed questions. They help compare systems, but they do not capture all real user behavior. People change goals, use shorthand, share devices and refer to the same project by different names. Benchmarks can test some of these cases, but no single score covers the full problem.

Results also depend on the model, memory store, search method and scoring method. A system may improve recall while becoming worse at privacy. It may answer factual questions better but still make time errors. Several recent papers are preprints. Their results may change after review. Do not treat one benchmark score as a verified claim about a commercial assistant.

There is no universal rule for what a system should remember. A preference can be useful in one setting and sensitive in another. Law, product policy and user consent affect the design. Technical performance alone cannot settle these choices.

21. Wider effects

For individuals, memory can reduce repeated explanation and help with project continuity. It can also make a wrong assumption last longer. Users need a way to inspect and correct the record.

For companies, memory can preserve decisions across handovers. Shared memory also raises questions about ownership and access. A fact shared with one employee may not be suitable for another. Private and team records should remain separate.

For public services, memory may reduce repeated form filling. It may also create a record of sensitive interactions. People should know what is retained, who can see it and how to correct it. This is especially important when people cannot easily change providers.

For developers, persistent memory changes the security model. A short-lived prompt may hold data for one task. A memory store can retain it for months. Teams must protect the store, limit retrieval, monitor access and test deletion.

22. A practical test plan

Write a policy before building memory. Define what the system may store, which data needs permission, how long records remain and who can access them. Then test at least six tasks: exact recall, cross-session reasoning, date reasoning, updates, irrelevant memories and requests to forget. Include cases where the right answer is "not known".

Measure extraction precision: how many stored facts are valid and useful? Measure retrieval recall: how many needed facts are found? Measure answer accuracy after retrieval. Measure update accuracy: does the current record reflect the latest valid information? Measure deletion success: can the fact still be recovered? Report these measures separately. One score can hide a serious privacy failure.

Use difficult cases. Test similar names, old dates, indirect wording, two people on one project, and a preference that changes twice. Test a fact copied into several memory types. Keep a record of the model version, memory version, retrieved items and evaluation result.

Finally, test with intended users. Obtain consent, minimise the data, and allow people to correct records. Release a memory feature only when the team can explain what it stores, why it retrieves a fact and how it removes that fact.

Key lessons

  1. Context and persistent memory solve different problems.
  2. Store facts with a source, date, confidence and permission rule.
  3. Do not keep every conversation by default.
  4. Keep old and new versions when facts change.
  5. Check whether a memory applies before using it.
  6. Similarity scores help search; they do not prove truth.
  7. Let users inspect, correct and delete records.
  8. Test deletion across transcripts, summaries, indexes and backups.
  9. Measure recall, updates, privacy and abstention separately.

Five questions and answers

1. Why is a large context window not persistent memory?

A context window is temporary input for one response. Persistent memory stores selected information outside the prompt and retrieves it in later sessions. It also needs update, access and deletion rules.

2. What should a memory record contain?

It should contain the fact, source, statement date, validity period, confidence, sensitivity label and access rule. These fields help the system check and update the fact.

3. Why can semantic search return the wrong memory?

It finds text with related meaning. It does not prove that the record is current or true. The system must check dates, sources, identity and context.

4. What is the difference between recall and memory awareness?

Recall means finding a stored fact. Awareness means deciding whether that fact applies to the current request. A system can recall a fact and still use it at the wrong time.

5. Why is deleting one sentence not always enough?

The fact may also exist in a summary, index, graph, cache or backup. Deletion must trace and remove related copies, then test whether the information can still be recovered.
